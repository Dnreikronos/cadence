# Company wallets sign the USDC wrap transaction

Status: implemented and verified locally; browser-wallet devnet acceptance pending.
Date: 2026-09-29. Implementation owner: Codex in the current session.
Issue: [#52](https://github.com/Dnreikronos/cadence/issues/52).

Deliver unsigned transactions that exchange company USDC for the deployed
wrapped USDC mint at 1:1, configure the destination when necessary, and persist
the verified transaction signature. Follow [ADR B9](../decisions/2026-09-27-confidential-payroll-rail-architecture.md):
the company wallet signs; the proof service never receives its signing key.

## Existing pieces and gaps

[The mint tool](../../ops/mint/src/token_wrap.rs) already defines the deployment,
PDA derivations, associated-account creation and wrap instruction. Reuse those
definitions instead of maintaining a second instruction layout. The service's
[v1 compiler](../../services/proof/src/solana/v1.rs) creates empty signature
slots and enforces the transaction size limit.

[Key derivation](../../services/proof/src/keys/elgamal.rs) currently discards
the derived AES balance key. [Vault access](../../services/proof/src/keys/vault.rs)
stores only the ElGamal secret and requires trusted authentication and account
authorization from its caller. There is no HTTP enrollment or authentication
implementation in the current service. The [key-storage contract](2026-09-28-050-encrypted-viewing-keys.md)
must be extended if this work adds persistent AES-key access.

The [spike](../../spikes/confidential-transfer/src/main.rs) separates wrap/funding,
confidential deposit and apply-pending. Wrapping alone creates a public token
balance. [#68](https://github.com/Dnreikronos/cadence/issues/68) owns apply-pending;
a confidential deposit remains pending until that operation runs.

## Local implementation scope

The user authorized local implementation on 2026-09-29, leaving every change
uncommitted. Include confidential deposit into pending balance; applying it
remains #68. Configuration accepts a public validity proof and encrypted zero
balance prepared by the wallet activation flow. No viewing secrets enter these
endpoints, so this work does not change #50's storage format or add enrollment.
The wallet must use its enrolled ElGamal key when producing the setup proof.

Transaction assembly uses public inputs. The wallet signature on the exact
prepared message authorizes the funds movement; confirmation is permissionless
but can only record that verified public fact. Supabase JWT and company
membership routing remain #63/#75. No record-listing or secret-reading endpoint
is exposed here. This supersedes the earlier proposed JWT prerequisite.

Persist unsigned transactions and confirmation metadata through Supabase
PostgREST, using a restricted `cadence_wrap_service` JWT with RLS denying client access.
Use finalized chain reads for confirmation. Local tests use mock RPC/REST
servers and a disposable PostgreSQL database for migration permissions.

## Implementation sequence

1. Settle the request contract and key prerequisite. Use a deterministic
   Token-2022 associated account so the browser needs only its wallet signer;
   create it idempotently, then reallocate for the confidential extension when
   absent. Validate existing account owner, mint and confidential configuration.
   Verify fresh, existing and mismatched accounts with realistic account data.
2. Build `POST /wrap` in the issue's proposed `src/routes/wrap.rs`. Represent
   amounts as integer base-unit strings to avoid browser floating-point loss;
   reject zero, overflow and any confidential-deposit limit violation. Return
   base64 unsigned v0 bytes, required signer order and blockhash expiry context.
   Verify instruction accounts, amounts, proof offsets and empty signatures by
   decoding the returned transaction, including repeat deposits.
3. Add durable request/confirmation records with client access denied and an
   idempotent `POST /wrap/confirm`. Bind the submitted signature to the prepared
   transaction, verify successful on-chain execution before recording success,
   and reject unrelated or failed transactions. Verify retries, cross-wallet
   access and database failure against a disposable database. The migration
   grants only wrap-record access to the dedicated REST role; broad service_role
   credentials must never enter the proof runtime.
4. Run formatting, compiler and Clippy checks, plus only the tests affected by
   these changes. Verify each implementation phase before moving to the next;
   keep each phase within five changed files. Finish with browser-wallet devnet
   evidence if an authorized wallet and funded account are available. Local
   transaction tests alone do not satisfy the issue's browser acceptance check.

## Review follow-up

Bound unauthenticated wrap work before RPC or storage access with process-wide,
peer-IP and wallet quotas and a concurrency cap. Use the socket peer, never an
untrusted forwarding header. Keep limiter state bounded by the global quota.
Schedule cleanup once a minute using the finalized devnet block height. A
restricted database function deletes at most 1,000 unsigned expired records per
call, retaining them for 24 hours to allow delayed confirmation. Confirmed
receipts stay immutable and are never collected. Document proxy and replica
limits and verify rejection before RPC plus cleanup permissions and retention.

The review follow-up passed all-target compilation, Clippy and formatting.
Two limiter unit tests and two HTTP tests cover quota reset, bounded peer state,
wallet rejection before RPC, and spoofed forwarding headers. Existing wrap HTTP
tests still pass. Cleanup transport tests verify finalized height, the devnet
guard and storage failure propagation. The real PostgreSQL 17 test verifies
1,000-row batches, the grace period, retained confirmed/unexpired rows, denied
cleanup access for other roles and continued denial of direct deletion.
