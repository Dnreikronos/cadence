# Confidential payment runs

Issue: https://github.com/Dnreikronos/cadence/issues/55.

Use the merged #53 proof builder and #54 authenticated transfer service. The
user authorized including these dependencies; no replacement implementation
is needed. Supabase verifies the bearer token, the existing wallet association
authorizes the payer, and each key read uses the durable audit accessor.

`POST /runs` accepts the transfer's wallet, sender, transient AES key and optional
wallet-link signature, plus 1–100 ordered `{recipient, amount}` entries. Return
one unsigned v1 transaction for each buildable payment, with position, required
signers and blockhash expiry. A recipient or proof failure affects only that
payment. Reject malformed amounts, duplicate recipients and oversized batches
before expensive work. Never persist amounts, AES keys or association signatures.

Proofs bind to the sender's exact ElGamal balance. Build each successful payment
against the preceding transaction's resulting ElGamal and AES ciphertexts;
skip failed preparations without debiting the predicted sender. The browser
approves once and signs/submits in order, waiting for finalized execution before
submitting the next payment. A failed submission invalidates later predictions.
Do not send those stale transactions. Reprepare unpaid payments in the same run
through `POST /runs/:id/retry`, resupplying their transient amounts and AES key.
An existing attempt can be replaced only after a verified finalized failure or
finalized block-height expiry, preventing two live transactions for one payment.
Retry requires the original wallet signature for every still-prepared attempt,
including unsent transactions. Observe finalized expiry before reading history;
reconcile landed successes instead of replacing them. An expired blockhash alone
does not prove that a payment never landed.

`POST /runs/:id/confirm` accepts position/request-ID/signature entries. Verify exact prepared
messages and wallet signatures even for chain failures. Record each finalized
success/failure independently; a pending, invalid or unavailable RPC result for
one signature must not prevent another payment's receipt. Return fixed per-item
errors and status, never provider bodies or amounts. Confirmations are immutable
and idempotent; persist every successful update before returning it.

`GET /runs/:id` returns ordered payment statuses, signatures and slots, without
amounts or transaction payloads. Scope every database operation to the verified
user. Add runs/payments with RLS and a restricted runtime role; no direct client
writes, no Vault access for receipt credentials. Preserve previous attempts for
reconciliation. Reuse the transfer runtime configuration and bounded CPU workers.

Verify rolling proof state and failure skips, three-recipient preparation and
confirmation, partial failures, retries without duplicate payments, cross-user
denial, immutable receipts, secret-free storage/errors, quotas and migration
permissions. Run formatting, compiler, Clippy and targeted tests. Report real
devnet/provider acceptance separately from local transaction signing/mock RPC.

## Verification outcome

Implemented preparation, confirmation, status and retry endpoints, rolling
ciphertext state, private run/payment storage and immutable attempt history.
The runtime reuses the merged proof/transfer dependencies and shared CPU slots.
The [API contract](../dev/RUNS_API.md) documents the browser's signing order and
safe recovery under one approval.

Rust formatting, all-target compiler checks and Clippy with warnings denied
passed. Eighteen targeted tests passed: fifteen tests across batch, runs HTTP,
transfer HTTP/auth, confidential proofs and compatibility, plus the explicitly
run storage, Vault-backed runs HTTP and Vault-backed transfer HTTP integration
tests. No full local test suite was run. CI YAML parsed successfully and adds
isolated run-storage and Vault run tests. Remote CI covers the full proof
suite, image health check and Supabase migration/RLS checks.

The real PostgreSQL test verifies RLS, owner reads, cross-user denial, atomic
rollback, immutable successes and concurrent retry exclusion. The real Vault
test verifies audited key access, three-recipient generation, exact-message
receipts, failure isolation, same-run recovery, history preservation and
reconciliation of a transaction that landed before expiry. Proof tests verify
all three proofs and exact ciphertext subtraction between successive transfers.
The existing dependency deprecation warning remains in vendored token-client.

On 2026-10-03, the actual run endpoints executed three live devnet payments
from one browser approval through the existing Turnkey root test adapter.
Run `0b6bf3e1-5f65-47a2-a14e-c1877f33b96a` finalized at slots 507099198,
507099212 and 507099225, with a separate receipt for every payment. Each
transaction was 2,913 bytes. Real disposable Supabase Auth and Vault backed
the check. Decrypted recipient credits and sender debit matched; all nine
proof contexts closed; independent RPC exposed ciphertext without amount
fields. The [public evidence](../dev/spikes/2026-10-03-runs-devnet.json) records
the signatures and validation results.

This browser harness checks the batch contract and Turnkey v1 compatibility.
Production user-controlled embedded onboarding remains #77, and the product
approval UI remains #83. Every migration also applied to the fresh local
Supabase database. Hosted migration/deployment still require an identified
target and credentials; neither Supabase nor Fly CLI is logged in locally.
