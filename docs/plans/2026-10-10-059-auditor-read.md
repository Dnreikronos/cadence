# Auditor read endpoint

Issue: https://github.com/Dnreikronos/cadence/issues/59.

Implement company-scoped auditor grants and authenticated payment reads. Include
admin grant creation, listing and revocation: #85 owns the designation UI and #69
owns email delivery, but neither specifies these backend operations. Grant APIs
operate on existing auditor identities; invitation delivery stays with #69.

Bind new runs and standalone transfers to the payer's company when prepared.
Company attribution is immutable. Existing unattributed receipts remain hidden
from auditors rather than guessing their historical company from today's
membership. Recipient-originated transfers remain outside company audit history.

Use a dedicated `cadence_audit_service` database role, with RLS driven by the
verified Supabase user. Auditor membership alone is insufficient: an explicit
grant for the requested company is required. Invite acceptance creates that
grant; revocation removes it without changing the caller's identity or wallet.
Missing grants and wrong-company requests both return 404 before key access.

Return finalized payroll and standalone payments through
`GET /audit/:company/payments`, with bounded UUID cursor pagination. Decrypt the
sender handle of the stored transfer proof, never the balance or a mint-wide
auditor key. No chain calls, wallet or wallet signature are required of auditors.
Use actual recipient metadata where available, otherwise the destination address
with a null person ID. Amounts are transient base-unit strings in successful
responses, with `Cache-Control: no-store`.

One authorized page request, including an empty page, writes one company-scoped
row to #49's append-only log. Commit it before decrypting any Vault secret.
An opaque, short-lived, single-use permit pins the selected receipt IDs and is
bound to the authenticated auditor and company. Recheck the grant at consumption.
Multiple sender keys share this one request audit record. Failure to persist the
audit record prevents decryption. Denied requests decrypt nothing.

Verify two-company RLS, grant lifecycle, identical credentials before/after
revocation, multiple keys in one page, pagination, empty reads, immutable company
attribution, and audit-before-decrypt under real disposable Supabase/Vault.
Run Rust formatting, all-target compilation and Clippy, and targeted tests only.
Preserve the existing local work on wrap, runs and indexer.

## Verification outcome

Implemented and verified locally against real disposable Supabase PostgreSQL
17.6.1.143 and Vault 0.3.1. Twenty-one pgTAP authorization checks pass, as do the
ordinary HTTP/configuration/ciphertext checks and the explicitly executed Vault
integration test. The existing invitation suite's 46 assertions also pass after
matching the disposable image's Auth fixture to the running Supabase stack
(`email_confirmed_at` and the current `auth.uid()` claims fallback). The test
proves a caller with the identical bearer token loses
amount access when its grant is revoked. Multiple sender keys and an empty page
each produce one durable audit row. Compiler and Clippy checks pass; the existing
vendored token-client deprecation warning remains.

The grant-page query explicitly types its SQL limit as `integer`: PostgreSQL's
implicit LIMIT parameter type is `bigint`, which rejects the Rust `i32` parameter.
The real database HTTP test covers this boundary rather than relying only on
in-memory pagination checks.

The full suite was not run. The Rust integration test synthesizes finalized
receipts from real cryptographic proof fixtures. The separate
[live devnet acceptance run](e2e-59-2026-10-10/report.md) submitted a fresh
confidential payment of 12345 base units and verified its finalized transaction
at slot 509631000. All three headed-browser scenarios passed. The same auditor
bearer read the exact amount before revocation and received 404 afterward;
Supabase still accepted the bearer for the same actor. A reload and independent
API/database rereads confirmed the revoked grant stayed absent, with no audit
rows from denied reads.

The migration and dedicated role were provisioned locally. The Auth schema grant
needed its local owner, and the loopback database connection needed explicit
`sslmode=disable`. No hosted migration or deployment was performed. See
[AUDIT_API.md](../dev/AUDIT_API.md) for the API, provisioning requirements, and
historical-attribution limitation.
