# Chain indexer

Issue: https://github.com/Dnreikronos/cadence/issues/58.

Status: implemented, migrated and verified against live devnet and the connected
local run dashboard. Hosted deployment remains outside this local task.

Cover payroll runs and standalone wrap, transfer and unwrap requests. Issue
#147 owns the frontend's proof of nonexecution before retrying standalone
requests; it does not provide background indexing.

Persist a cryptographically verified submission signature before confirmation
RPC work. Keep submission evidence separate from the terminal receipt. Existing
confirm APIs stay compatible; a pending response still means pending, and another
signature cannot replace the first. Discover transactions whose clients never
called confirm through paginated finalized wallet history, matching the complete
prepared message and its wallet signature. Persist wallet history cursors only
after the entire pass succeeds. Never infer failure from missing history or an
expired blockhash.

Use finalized signature subscriptions as wakeups, then verify the exact signed
transaction through the existing confirmation verifier before writing either
success or failure. A dedicated indexer database role can read public transaction
metadata and update receipt columns, with no key/Vault access. Reconcile on
startup before binding the HTTP listener, and after reconnects; periodic server
backfill catches dropped notifications and newly submitted signatures. Keep
provider URLs, RPC errors, amounts and keys out of logs and stored events.

The payment row is the source of truth. Run status remains derived from its
payments. Standalone requests gain terminal status so failed transfers cannot
enter incoming-payment history. Database triggers write one immutable, typed
event per terminal attempt in the same transaction as its receipt. The outbox
survives restarts and can be consumed by #69 without email code in the indexer.
Enable payment updates in Supabase Realtime when its publication exists.

The shipping branch starts from current main, whose run API client already uses
the implemented backend contract. Keep that read path and refresh run metadata
every five seconds while any payment is prepared. Refetch on mount, focus and
reconnect so reopening a dashboard observes background recovery. A failed refresh
must preserve the last run and keep checking a pending payment. Stop periodic
reads once every payment is terminal. The earlier local acceptance used a temporary
Supabase adapter against the older frontend; it is not needed in the shipping branch.

Verify real disposable PostgreSQL migrations, permissions, immutable receipts,
concurrent updates, outbox rollback/idempotency, all four transaction kinds,
pending signatures, cursor pagination, missing/malformed/mismatched history,
WebSocket notifications/disconnects, and restart backfill. Run formatting,
all-target compilation and Clippy, plus tests targeted to the affected routes
and indexer. Leave unrelated existing local edits intact.

## Review follow-up

An initial retryable run read must keep its polling schedule even when there is
no cached run. Permanent authorization and missing-run errors stop polling.

Bound unsigned discovery by the prepared requests' blockhash validity windows.
Use a conservative 300-block history allowance before each stored expiry, and
read finalized block headers to compare block heights rather than treating
slots as heights or trusting wall clocks. Skip transaction bodies outside every
pending window. When an old block is pruned, the first retained block can prove
it predates the relevant window; missing relevant history still blocks readiness.
Save the descending page position separately from the completed wallet cursor,
so a later page failure resumes without skipping unprocessed payments.
Revisit bounded pending windows after a completed pass and catch up after a
resume, since a preparation can commit after the earlier pending read. Retry
provider throttling on block headers with bounded `Retry-After` handling.

Keep the startup recovery gate, since the issue requires recovered receipts on
the first read after restart. Background recovery and WebSocket handling run
independently. Refresh active subscriptions every five seconds, reconcile active
requests every thirty seconds, and include old unresolved requests in recovery
every five minutes. A 150-block finalized-height grace period removes expired
requests from fast work without turning absence into failure. Fast unsigned
scans do not advance the durable full-recovery cursor.

Verify initial read failures, irrelevant/pruned history, page resume after a
failure, expiry selection, slow recovery of old landed requests, and WebSocket
delivery during slow or failing discovery. Re-run the compiler, linters and
targeted tests before pushing the review fixes.

The review follow-up passed the stated regressions, compiler and lint gates.
Live startup recovered from actual provider throttling after adding bounded
header retries. The open dashboard moved from its initial connection error to
Confirmed without a reload; all six events remained unchanged. See the
[review check](e2e-58-2026-10-10/review-check.md) for the exact validation scope.
